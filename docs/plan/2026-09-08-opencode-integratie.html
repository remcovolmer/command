OpenCode toevoegen aan Command wordt een 4e agent in het bestaande registry — geen refactor nodig

Command is al gemigreerd van Codex|normal naar een generiek registry-model (AgentType = 'claude' | 'codex' | 'pi'). OpenCode lift daarop mee: gefaseerd eerst hookless (pi-pariteit, uren werk), daarna pas de plugin-hook en headless-automations. Dit plan is MECE per bestand, met open spikes expliciet timeboxed.

Status: plan — geen code gewijzigd Scope: chat + state-indicator + restore + automations Bronnen: codebase + opencode.ai/docs (sept 2026)

1. Command heeft geen “Codex-integratie” meer — er is één generiek agent-seam, en dát versnelt alles

Situatie. Command beheert PTY-chats voor meerdere coding-agents in één Electron-window. Vroeger stond er type === 'Codex' door de code; nu is alles isAgentType() / AGENT_IDS-gedreven. Complicatie. “OpenCode toevoegen” klinkt als een grote feature, maar het echte werk zit op drie plekken met elk een ander risicoprofiel: (a) spawn/resume-vlaggen, (b) state-detectie — OpenCode heeft géén hooks.json maar een plugin-systeem op Bun, (c) headless-runs voor automations met een ander JSON-contract. Resolutie. Gefaseerd leveren: Fase 1 hookless = direct bruikbaar zonder enig OpenCode-specifiek state-werk; Fase 2/3 voegen precisie toe.

Kernbevinding (geverifieerd in code): shared/agents.ts:21 (AGENT_IDS), shared/ipc-types.ts:72 (AgentType) en electron/main/services/agents.ts:35 (AGENT_SPAWN: Record<AgentType,…>) forceren via het type-systeem een entry voor elke agent — een ontbrekende OpenCode-entry is een compile-error, geen runtime-verrassing. TerminalManager, store, IPC en de meeste UI hoeven niet te veranderen.

5. Fase 2 is het enige echte OpenCode-werk: een Bun-plugin in plaats van een hooks.json-entry

OpenCode kent géén ~/.codex/hooks.json-equivalent. State loopt via plugins (officieel gedocumenteerd, opencode.ai/docs/plugins): bestanden in ~/.config/opencode/plugins/ (globaal) en .opencode/plugins/ (project) worden automatisch geladen; npm-plugins via plugin:[…] in opencode.json. Relevante events: session.created / session.status / session.idle / session.updated / session.error, permission.asked / permission.replied, tool.execute.before/after.

De .cjs-kopieer-aanpak is dus niet 1-op-1 herbruikbaar: de plugin moet Bun-compatibele fs-writes doen en mag nooit de sessie breken (silent-fail, zoals de bestaande hooks). Spike S2 moet dit als eerste bewijzen.
Meelifters zonder wijziging: watcher-poll (250 ms), INPUT_STATE_GUARD_MS-race-guard, registerTerminal / preAssociateSession / getTerminalSessions en before-quit-persist (main/index.ts:2084) zijn agent-agnostisch — hookless pi wordt vandaag overgeslagen, opencode gaat na hasHook:true vanzelf mee.

8. Volgende stap: opportunity-window van 10 minuten — of timeboxed Spike 0

Optie A — kleinste eerste stap (10 min, aanbevolen): voer Fase 1, items #1–#4 door (4 bestanden) en check npm run typecheck. Geen OpenCode-installatie nodig om de compile-gate te bewijzen; runtime-test volgt met opencode --version op je machine.
Optie B — eerst zekerheid (2u): draai Spike S1–S5 en leg de vijf antwoorden vast in docs/solutions/ (met YAML-frontmatter module/tags/problem_type). Daarna Fase 1–3 zonder herwerk.

Aanbeveling: A, daarna B — A bewijst dat het registry-model klopt (en is omkeerbaar in één commit); B voorkomt dat Fase 2 op aannames over Bun-plugin-payloads bouwt. Eén ding tegelijk, geen scope-creep in dezelfde PR (bugfix ≠ refactor).
